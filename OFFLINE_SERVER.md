The offline server contract is public.sync_booking_event(p_event_id uuid, p_booking_id uuid, p_expected_version bigint, p_action text, p_payload jsonb, p_predecessor_id uuid default null). The first five parameters are required. Authenticate using the staff user's own session. Never use a service key or accept an actor or role from the client.

The result is JSON containing event_id, booking_id, version, result, booking, operations, and lifecycle_revision. booking is the authoritative bookings row after all triggers. operations is its current booking_operations row or null. result preserves the underlying RPC's native result. version equals booking.sync_version. lifecycle_revision is the number of handover undo receipts. Dates use normal PostgreSQL/Supabase timestamp serialization. An exact replay returns the original response byte-for-byte as JSONB, not the current booking. Therefore invalidate/refetch current queries after acknowledgment rather than replacing newer cached rows with an older replay result.

The migration adds bookings.sync_version, a nonnegative bigint defaulting to zero. It is server-controlled on insert and increments on every booking update. Operations inserts, updates, and deletes also update the booking through a protected trigger, so old clients' operations invalidate offline baselines. Do not predict increments. One logical RPC can advance the version several times. Read it from the response, or from a fresh booking query. Existing select('*') calls include it automatically; explicit projections must add it. Existing records receive a metadata default without data backfill. No existing columns or mutation APIs are removed.

The JSON payload must contain exactly the fields described below. All listed keys are required, even when their value is null. There are no defaults. Request and booking IDs are forced from the envelope. Nested details, expected snapshots, patches and media retain the existing RPC's validation rules.

payment delegates to record_booking_payment. Its fields are amount_cents, method, expected_paid_cents, expected_total_cents. Amounts are integer cents, not euros. Method is cash, card or bank_transfer.

customer_call delegates to record_booking_customer_call. Its fields are expected_called_at, expected_checked_out_at, expected_lifecycle_revision, allow_repeat.

clear_customer_call delegates to clear_booking_customer_call. Its fields are expected_called_at and expected_lifecycle_revision.

handover delegates to complete_booking_handover. Its fields are action, details, media, expected_in, expected_out, expected_revision. Action is in or out. Details and media are JSON object/array values, not serialized strings. The event UUID is also the handover request UUID.

undo_handover delegates to undo_booking_handover. Its fields are action and expected_at.

detail delegates to apply_booking_detail_action. Its fields are action, target and expected. Action is status or spot. Its expected object contains status, checked_in_at, checked_out_at, spot, lifecycle_revision, detail_revision exactly as in the existing client.

safe_edit delegates to apply_booking_safe_edit. Its fields are patch and expected. Its expected object contains edit_revision, detail_revision, lifecycle_revision, status, checked_in_at, checked_out_at, spot. Driver edits remain limited to km, key_cash and comment. Other permitted editable fields still require admin. Money, status and lifecycle fields cannot be edited through this route.

operation delegates to record_booking_operation. Its sole field is action, restricted to taken_away, retrieved or ride_started. Calls must use the dedicated customer_call action with explicit repeat intent.

update_ops delegates to update_booking_ops. Its sole field is patch. Existing field allowlists and historical cash guards still apply. Prefer detail for spot changes and safe_edit for ordinary edits when the existing UI already uses those APIs. Do not use this legacy route to evade the original screen's confirmation flow.

The function first verifies active staff and validates the envelope. A global event UUID transaction lock serializes duplicate submissions. An existing receipt is returned only if auth.uid(), booking ID, action, original expected version, predecessor ID and full JSON payload all match. Changed reuse raises 23514. A receipt cannot be read directly, updated or deleted through REST, including by admins. An inactive account cannot replay a receipt. A previously authorized response can be replayed after role demotion while the account remains active staff, because it performs no new effect.

For a new event, the function validates the explicit dispatch allowlist, acquires the original RPC's UUID advisory lock when relevant, rejects UUIDs already used directly in that underlying RPC ledger, locks the booking FOR UPDATE, and compares its sync_version to p_expected_version. A mismatch raises PT409 before mutation. It then calls the existing RPC with its normal permission, lifecycle, immutable receipt, amount, field and storage checks. The effect and offline receipt commit together in the same database transaction. Any error rolls both back. The response is recorded only after success. No dynamic SQL, generic arbitrary RPC name or client authorization claims are accepted.

PT409 means review required, not a network retry. Retain the local event and its media, show the server booking, and require a user resolution. A failed event has no receipt and may be retried unchanged after a transient problem. Network errors and a lost success response must reuse the original event UUID, payload and expected version. Do not mint a new UUID on retry. 42501 means expired/invalid permission or inactive staff; pause the outbox for login or authorization. 23514 means a lifecycle/money/media/business-rule failure or identity collision. 22023 means malformed/unsupported input. Other SQL type errors are invalid input, not retryable success. Missing RPC/schema cache errors mean the migration is not installed; block synchronization and report it. Never fall back to unsafe legacy calls.

Persist each event under the authenticated user ID and deployment/project ID. Never sync another staff member's queued work after account switching. Serialize events per booking, and block later events after a conflict. Several offline events captured from one snapshot need explicit queue sequencing. The optional p_predecessor_id names the previous confirmed event on this booking under the same actor. When supplied, the original expected version must equal the predecessor's original expected_version or its committed response version. The server compares the CURRENT booking version to that predecessor's committed response version, not to an automatically fetched baseline. Missing, different-booking or different-actor predecessors raise PT409. An intervening writer also raises PT409. This permits explicit dependent chains without ignoring external changes. Inner RPC expected timestamps and revisions still must match the authoritative server state; local predicted call/check-in timestamps are not server timestamps and may intentionally conflict when used by a subsequent clear/undo/handover. Do not silently replace those snapshots. Do not auto-fetch a fresh version and retry a rejected event, because that disables conflict protection. Failed or unresolved events must remain visible.

Stage handover blobs into the existing private booking-media bucket before calling the event RPC. Use the canonical path BOOKING_UUID/EVENT_UUID-MEDIA_UUID.ext and existing MIME/size/captured_at metadata. Preserve IDs across retries, upload without overwrite, and verify that an already-existing object is the same upload. The completion RPC validates exact stored size/MIME and the path against this event UUID before linking it. No new upload endpoint or relaxed bucket policy is introduced. If staging fails, do not call completion. A missing/mismatched staged object fails atomically without confirming handover. Failed events may leave staged objects; do not delete media linked to any committed receipt. Orphan cleanup is a separate, explicitly authorized operation. Storage uploads are not part of the SQL transaction and are not claimed to be exactly-once effects.
