# Persisted staff operational actions

`src/lib/operations.ts` exports `loadBookingOperations()` and `recordBookingOperation(bookingId, action)`. Actions are exactly `taken_away`, `customer_called`, `ride_started`.

The server RPC is `record_booking_operation(p_booking_id uuid, p_action text)`. It returns one `booking_operations` object with booking_id, taken_away_at, customer_called_at, ride_started_at (nullable UTC ISO timestamps), performed_by (latest action actor), updated_at, and an internal id. Caller does NOT provide timestamps, employee IDs or arbitrary patches. Server uses clock_timestamp and auth.uid. Load via `from('booking_operations').select('*')`, keyed by booking_id, then merge into the frontend view only. Never include operation fields in booking upserts. Missing row means no recorded actions.

The RPC requires active staff, confirmed booking not checked out, and an existing vehicle check-in for taken-away/ride-started. Customer-called can be recorded before check-in. Repeat action is idempotent and preserves the first timestamp/actor for that action, including a retry after checkout. No undo/backdating API exists. All staff can act on shared bookings, matching existing check_booking staff access; immutable history attributes each event to its authenticated actor. There is no extra assigned-driver-only restriction.

Tables `booking_operations` and `booking_operation_events` are staff-readable through RLS but not directly writable by authenticated users, including admins. Each action has one immutable event with original actor/time. Audit triggers additionally record inserts/updates/deletes in the existing admin-only audit_log. Trusted service role/database owner retain administrative authority, not end-user edit controls. Deleting a disposable/test booking cascades its operation/event records, while audit_log preserves the administrative deletion trail.

No existing booking row values are updated by the migration or action RPC.
