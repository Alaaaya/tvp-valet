# Narrow existing-booking edits
Apply migrations through 240000 in order after synchronizing main's 190000/200000 lifecycle migrations. This work never applies migrations itself.

Add optional numeric edit_revision to Booking. load select('*') already loads it. Load lifecycle_revision from the existing lifecycle receipt count, never assume zero for an existing booking. Existing edits must call saveEditedBooking(original, {...original,...patch}, requestId), and replace local state with its returned server booking. Do not call full-upsert saveBooking for existing edits. Keep original snapshot, same edited state and UUID when retrying a network failure. On PT409 reload and ask user to review rather than automatically replay a stale draft. New bookings keep existing INSERT path.

Editable fields are customer_name, explicit first_name/last_name (120 each), car_description (500), phone, email, persons, plate, km, key_cash, comment, arrival_at/departure_at, flight_in/out. Actual flight timestamps are not edited by the current view and are deliberately excluded. Driver edits only km/key_cash/comment. Remove or disable Spot on BookingEditView; location changes use dedicated audited action, never this helper. total/paid/product/covered/platform/driver/status/lifecycle/call/operational fields cannot be patched.

Server-owned edit_revision advances on any editable-field change, including privileged/legacy writes, and ignores submitted revision numbers. This prevents ABA even if a field returns to the original value. Expected edit/detail/lifecycle revisions and status, checked timestamps, spot are checked while row locked. Payment updates and customer-call changes may coexist because this RPC never writes them. Immutable receipts bind UUID, server actor, booking, complete patch, complete expected state, and before/after snapshots. RPC returns JSON with current booking plus authoritative lifecycle_revision counted under its booking lock on fresh saves and replay. The helper validates returned revisions and never fabricates a lifecycle count. Identical retries return current booking without repeating writes; any changed context rejects. Receipts and generic audit retain the original snapshot. No public receipt access; admin-only RLS read.

Numeric legacy key_cash clearing/changing is still blocked by the payment migration's guard. Never bypass or disable that guard for edits. All existing constraints apply, including finite valid chronological dates and integer km/person limits. Unchanged imported legacy values are kept, not normalized or split.

Date policy is intentionally fail-closed even for unrelated edits when the stored dates are nonfinite or reversed. Existing DB chronology constraint is preserved, not bypassed. Such legacy data requires explicit date repair rather than silently persisting another edit; current BookingEditView also validates whole draft dates.
